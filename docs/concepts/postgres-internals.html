Postgres Internals

MVCC · Vacuum · Locking · Indexes · Query Planner

Why this matters
Most production database incidents that look like app bugs are one of: a bloated table, a lock queue, or a bad query plan. MVCC explains all three root causes.

Basics Refresh

Postgres is an ACID-compliant relational database. A quick refresh on what that means at the storage level before going deeper.

How data is stored

Tables are stored as heap files — a collection of 8KB pages. Each page holds multiple tuples (rows). An index is a separate file with a B-tree (or other structure) pointing to heap locations.

PropertyWhat it means in Postgres
AtomicityAll writes in a transaction commit or none do. WAL ensures this survives crashes.

MVCC — Multi-Version Concurrency Control

The mechanism that lets readers and writers not block each other. Instead of locking rows, Postgres keeps multiple versions of the same row and shows each transaction the version it's allowed to see.

xmin and xmax

Every tuple has two hidden system columns:

ColumnMeaning
xminTransaction ID that created (inserted) this tuple
xmaxTransaction ID that deleted this tuple. 0 = still alive.

A transaction can see a tuple if: xmin <= my_txn_id AND (xmax = 0 OR xmax > my_txn_id).

UPDATE is INSERT + DELETE

Postgres never modifies a tuple in place. An UPDATE writes a new tuple version and marks the old one deleted by setting its xmax.

sequenceDiagram participant T1 as Transaction 100 participant Heap as Heap Page T1->>Heap: INSERT row A → tuple (xmin=100, xmax=0) Note over Heap: row A visible, alive T1->>Heap: UPDATE row A → new tuple (xmin=100, xmax=0)
old tuple: xmax=100 Note over Heap: old version dead for txn ≥ 100
new version alive

Snapshot isolation

When a transaction starts, Postgres takes a snapshot — a point-in-time list of which transactions are active. The transaction only sees committed data from before its snapshot. Reads are always consistent, never blocked by writers.

Key insight
This is why Postgres readers never block writers and writers never block readers. The cost is dead tuples accumulating on disk — that's what vacuum cleans up.

HOT updates

Heap Only Tuple update. If the updated column is not indexed and the new tuple fits on the same page, Postgres can skip updating the index entirely. The index still points to the old tuple, which chains to the new one. Significant write amplification saving.

Vacuum

MVCC leaves dead tuples behind. Vacuum reclaims that space. Without it, tables grow forever and performance degrades.

What accumulates

Autovacuum

Postgres runs autovacuum workers in the background. It triggers when dead tuples exceed a threshold (autovacuum_vacuum_scale_factor, default 20% of table). For high-churn tables, tune this aggressively:

-- Tune per-table for high-churn tables
ALTER TABLE transfers SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- trigger at 1% dead tuples
  autovacuum_analyze_scale_factor = 0.01
);

The long-transaction trap HIGH RISK

Vacuum cannot remove a dead tuple if any active transaction might still need to see it. A single long-running transaction (idle in transaction, forgotten query) will block vacuum from reclaiming any space created after that transaction started.

Incident pattern
Table grows unboundedly. Autovacuum runs but reports 0 tuples removed. Find the culprit with pg_stat_activity — it's almost always an idle transaction from a connection pool or a forgotten analytics query. 
-- Find blocking long transactions
SELECT pid, now() - pg_stat_activity.query_start AS duration,
       query, state
FROM pg_stat_activity
WHERE state != 'idle'
  AND query_start < now() - interval '5 minutes'
ORDER BY duration DESC;

-- Find oldest transaction preventing vacuum
SELECT min(backend_xmin) FROM pg_stat_activity;

txid wraparound CRITICAL

Transaction IDs are 32-bit integers — Postgres runs out after ~2.1 billion transactions. When this happens, Postgres will refuse all writes to protect data integrity.

graph LR A["txid 1"] --> B["txid 1,000,000"] --> C["txid 2,100,000,000"] C --> D["⚠️ WRAPAROUND
Postgres stops accepting writes"] style D fill:#2a1010,stroke:#f85149,color:#f85149

Postgres prevents this by freezing old tuples — marking them as visible to all future transactions. Monitor with:

-- Tables closest to wraparound (act if age > 1.5B)
SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 10;

The ALTER TABLE lock queue problem HIGH RISK

ALTER TABLE takes ACCESS EXCLUSIVE. If a long SELECT is running, ALTER TABLE queues behind it. Every subsequent SELECT then queues behind the ALTER TABLE — effectively taking the table offline.

sequenceDiagram participant S1 as SELECT (running, 5min) participant A as ALTER TABLE participant S2 as SELECT (new) participant S3 as SELECT (new) S1->>DB: Running (holds ACCESS SHARE) A->>DB: Waiting for ACCESS EXCLUSIVE Note over A,DB: ALTER queued — blocks here S2->>DB: Waiting (blocked behind ALTER) S3->>DB: Waiting (blocked behind ALTER) Note over S2,S3: Table effectively offline
Safe pattern
Always set lock_timeout before a migration. If the lock can't be acquired quickly, abort and retry during low traffic — don't let it queue.

SET lock_timeout = '2s'; ALTER TABLE ...

FOR UPDATE vs SKIP LOCKED

FOR UPDATESKIP LOCKED
BehaviourLocks selected rows, blocks other transactions trying to lock same rowsSkips rows already locked by other transactions
Use casePessimistic locking (prevent concurrent modification)Work queue — multiple workers pull jobs without blocking each other
-- Work queue pattern: each worker atomically claims a job
UPDATE jobs
SET status = 'processing', worker_id = $1
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;

Advisory locks

Application-level cooperative locks — Postgres stores them but your app decides what they mean. Useful for preventing concurrent runs of a job, or implementing distributed mutex patterns.

-- Acquire advisory lock (returns false if already held)
SELECT pg_try_advisory_lock(12345);

-- Release
SELECT pg_advisory_unlock(12345);

Indexes

B-tree (default)

Balanced tree. O(log n) lookup. Supports =, <, >, BETWEEN, ORDER BY, LIKE 'prefix%'. The right answer for almost everything.

Index types at a glance

TypeBest forNotes
B-treeMost things — equality, range, sortDefault. Use unless you have a specific reason not to.

BRINNaturally ordered large tables (timestamps, sequences)Tiny size, coarse — stores min/max per block range.

GiSTGeometric data, PostGISExtensible index framework.

Partial indexes HIGH VALUE

Index only rows matching a WHERE clause. Smaller, faster, cheaper to maintain.

-- Only index pending jobs (not the 99% that are completed)
CREATE INDEX idx_jobs_pending ON jobs (created_at)
WHERE status = 'pending';

Covering indexes (INCLUDE)

Store extra columns in the index leaf — avoid the heap fetch entirely for queries that only need those columns.

-- Query only needs id + status — never touches heap
CREATE INDEX idx_transfers_covering
ON transfers (account_id)
INCLUDE (id, status, amount);

When the planner ignores your index

  • Low selectivity — returning >5-10% of table rows, sequential scan is cheaper
  • Stale statistics — run ANALYZE
  • Type mismatch — WHERE id = '123' when id is integer
  • Function on column — WHERE lower(email) = 'x' skips index on email; create a functional index instead
  • LIKE with leading wildcard — LIKE '%foo' can't use B-tree

Query Planner

The planner chooses how to execute a query. It estimates the cost of each possible plan and picks the cheapest. Bad estimates = bad plans.

EXPLAIN basics

-- Show plan without running
EXPLAIN SELECT * FROM transfers WHERE account_id = 42;

-- Run it and show actual vs estimated
EXPLAIN ANALYZE SELECT * FROM transfers WHERE account_id = 42;

-- Full detail: actual rows, buffers, timing
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM transfers WHERE account_id = 42;

Row estimate mismatch — the root cause of bad plans

If rows=1 but actual rows=50000, the planner chose the wrong strategy. Fix: run ANALYZE tablename to refresh statistics, or increase default_statistics_target for skewed columns.

-- Refresh statistics
ANALYZE transfers;

-- Increase stats target for skewed column
ALTER TABLE transfers ALTER COLUMN status
SET STATISTICS 500;
ANALYZE transfers;

-- Inspect what Postgres knows about a column
SELECT * FROM pg_stats
WHERE tablename = 'transfers' AND attname = 'status';

WAL — Write-Ahead Log

Every change is written to the WAL before the data page is modified. This gives Postgres crash recovery (replay WAL to recover) and is the foundation for replication and CDC.

sequenceDiagram participant App participant WAL participant Heap participant Replica App->>WAL: Write change record (LSN assigned) WAL->>App: fsync ack (commit confirmed) WAL-->>Heap: Data page updated (async) WAL-->>Replica: WAL stream (replication)

LSN = Log Sequence Number. A monotonically increasing position in the WAL stream. CDC systems (Debezium) use LSN as the ordering and dedup key — never the event timestamp.

-- Current WAL position
SELECT pg_current_wal_lsn();

-- Replication lag (on primary)
SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;

  • You can read EXPLAIN (ANALYZE, BUFFERS) output and identify the bottleneck
  • You know why SKIP LOCKED beats FOR UPDATE for work queues
  • You can explain why UPDATE = INSERT + DELETE in Postgres
