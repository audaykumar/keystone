Kafka Internals: Partitions, ISR, and What an Ack Promises

Kafka is a replicated, partitioned commit log. Every guarantee it gives — and every one it quietly does not — follows from three mechanisms: partitions, leader-based replication with the ISR, and consumer group offsets.

TLDR

Quick brief
  • Ordering is per partition, never per topic. Same key → same partition → ordered. Different keys can interleave arbitrarily.
  • An ack means what you configured it to mean. acks=1 is a leader-only promise: kill the leader before followers copy the message and the acked message is gone. acks=all + min.insync.replicas=2 makes acked mean replicated.
  • Consumers own their position. Brokers delete by retention, not by consumption; the committed offset is just a number in a topic, and where you commit it relative to processing decides your delivery semantics.
  • Rebalances are the price of elastic consumers. Members joining or leaving redistributes partitions; flapping members redistribute them constantly.

Mental Model

Picture a topic as a set of independent append-only journals (partitions). A producer picks a journal by hashing the message key and appends at the end. Each journal has one broker acting as leader — all reads and writes go through it — and followers that copy new entries. A consumer group is a team of readers that splits the journals among themselves, each keeping a bookmark (offset) of how far it has read.

Nothing is ever handed to consumers; they pull from their bookmark. Nothing is deleted on read; entries age out by retention. This is why Kafka can replay: the bookmark can be moved backwards, because consuming never destroys anything.

Ground-Up Explanation

Partitions and keys

A partition is the unit of parallelism, ordering, and placement. The producer's hash partitioner guarantees one thing: equal keys land in the same partition and are therefore mutually ordered. Choose keys accordingly — an account id as key means per-account ordering, which is usually exactly the invariant a ledger needs. It also means a hot account is a hot partition; keys shape load distribution.

Replication and the ISR

Each partition has a replication factor (say 3): one leader plus two followers fetching its log. The in-sync replica set (ISR) is the leader's list of replicas that are fully caught up. When a broker dies, the controller elects a new leader from the ISR, which is what makes a clean failover lossless — anything the old leader acked with acks=all exists on the new leader by definition.

Kafka's committed watermark (the "high watermark") is the offset every ISR member has replicated. Consumers only ever see messages below it, so a consumer can never read a message that a failover might later erase.

The acks contract

SettingAck meansFailure behavior
acks=0message left the producerany hiccup loses messages silently
acks=1leader wrote it locallyleader dies before followers copy → acked message lost in a clean election
acks=all + min.insync.replicas=2the ISR quorum has itno acked loss on single-broker failure; writes rejected if ISR shrinks below 2 — an explicit error instead of silent loss

The last row states the real trade: acks=all converts data loss into visible unavailability. For payment events that is the correct direction to fail.

Consumer groups, offsets, rebalances

A group coordinator assigns each partition to exactly one member of a consumer group. Offsets are committed to the internal __consumer_offsets topic; on restart a member resumes from the last commit. When membership changes, the coordinator triggers a rebalance: partitions are revoked and reassigned. During a rebalance, affected partitions pause — a group that flaps (slow processing causing missed heartbeats, causing eviction, causing rejoin) spends its life rebalancing instead of consuming.

Lab Evidence

The runnable lab is labs/kafka/internals: a 3-broker KRaft cluster, a payments topic (6 partitions, RF 3, min.insync.replicas=2), and a Go driver producing sequence-numbered messages so loss and duplication are countable facts.

Two group members: watch the coordinator split 6 partitions 3/3, then hand them back when one leaves.

Measured: happy path and an uninvited lesson

Verified on 2026-07-07: the 3-broker cluster forms, leaders spread across brokers, and a 600-message keyed produce audits clean (600 unique sequences, 0 duplicates, 0 missing). The audit's per-partition counts taught something the page did not plan to: 10 keys hashed onto 6 partitions gave two partitions 180 messages and the rest 60 — a 3x hot-partition skew from key cardinality alone.

Production Notes

  • Partition count is close to permanent: you can add partitions (breaking key→partition mapping for existing keys) but never remove them. Size for target throughput ÷ per-partition throughput, with headroom.
  • Enable the idempotent producer (enable.idempotence=true, default in modern clients): retries stop creating duplicates within a partition session.
  • Watch consumer lag as a first-class SLO; lag growth is the earliest signal of a slow consumer, a hot partition, or a rebalance storm.
  • unclean.leader.election.enable=false (default) chooses unavailability over data loss when the ISR is empty. Turning it on is a data-loss decision, not a tuning knob.
