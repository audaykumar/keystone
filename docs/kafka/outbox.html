The Transactional Outbox: Killing the Dual-Write Gap

Any service that writes to its database and publishes an event performs two writes that no transaction spans. The outbox pattern closes the gap by making the event a database row, then letting change data capture do the publishing.

TLDR

Quick brief
  • The dual-write gap: commit to Postgres, then publish to Kafka — a crash between the two produces committed state with no event. Reverse the order and you get events for state that never committed. The gap moves; it never closes.
  • The fix is one insert: write the event into an outbox table in the same transaction as the state change. The database transaction is the only atomicity you need.
  • CDC does the publishing: Debezium tails the WAL through a replication slot and emits committed outbox rows to Kafka, in commit order.
  • CDC is at-least-once: connector restarts can re-emit rows. The outbox solves atomicity; consumers still need idempotency.

Mental Model

Stop thinking "save, then announce". Think "save the announcement too". The order and its order.created event commit as one atom or not at all; a separate process — one that can crash and resume freely, because its position is just a WAL location — carries committed announcements to Kafka. There is no moment where state exists without its event, because they were never two writes.

Ground-Up Explanation

Why retries cannot save the dual write

The subtle part of the failure is that good engineering hides it. A crashed writer restarts and retries idempotently: "order exists? skip." The skip is correct for state and fatal for the event — the one order that committed without publishing is now permanently silent. The lab reproduces exactly this: the restarted run finishes the remaining 499 orders perfectly, and order 500's event is simply gone.

What logical decoding provides

PostgreSQL's WAL already records every committed change in commit order. With wal_level=logical, a replication slot lets an external reader consume those changes as structured rows rather than physical pages. Two properties make this the right transport: only committed transactions appear, and the slot guarantees the reader misses nothing — Postgres retains WAL until the slot confirms it (which is also the operational hazard: a dead slot grows disk usage without bound).

The outbox table

CREATE TABLE outbox (
    id             bigserial PRIMARY KEY,
    aggregate_type text  NOT NULL,   -- 'order'
    aggregate_id   text  NOT NULL,   -- becomes the Kafka message key
    event_type     text  NOT NULL,   -- 'order.created'
    payload        jsonb NOT NULL
);

aggregate_id as the message key gives per-aggregate ordering in Kafka — all events for one order land on one partition, in commit order. Debezium's outbox event router SMT can route rows to per-aggregate topics and strip the envelope; the lab keeps the raw connector so the Debezium change format stays visible.

Implementation Details

  • The lab's connector watches only public.outbox (table.include.list), uses the built-in pgoutput plugin, and disables converter schemas so messages are plain JSON with the row under "after".
  • Delivery to Kafka is at-least-once: after a connector restart, rows since the last committed offset re-emit. Consumers dedupe on aggregate_id + event id — the idempotent-consumer pattern from the delivery-semantics page.
  • The outbox grows forever unless trimmed. Common approach: delete rows after CDC confirms them, or even DELETE immediately after insert in the same transaction — Debezium reads the insert from the WAL regardless.
  • Alternatives and their trade-offs: polling the outbox table (simpler, adds latency and load), listen-to-yourself (service consumes its own topic to update state — inverts the problem), and 2PC (heavyweight, and Kafka does not participate in XA anyway).

Lab Evidence

The runnable lab is labs/kafka/outbox: Postgres with logical WAL, Kafka, Debezium Connect, and a Go writer that hard-crashes after committing order 500 and before publishing its event. The audit is set arithmetic: every order_ref in Postgres must appear in the event topic.

Real runs from 2026-07-07. The restarted dual-write run finished the remaining orders perfectly and still could not recover ord-500's event — the idempotent retry skips the committed order and never re-publishes. The outbox run took the identical crash and lost nothing.

Production Notes

  • Monitor replication slot lag (pg_replication_slots): a stalled connector holds WAL and eventually fills the disk of the primary.
  • Schema-change discipline applies to the outbox table too; its shape is a public contract once consumers parse the payloads. A schema registry (Avro/Protobuf) replaces the lab's raw JSON in production.
  • Snapshots matter on first deploy: Debezium's initial snapshot emits existing rows; decide whether consumers should see history or only new events (snapshot.mode).
  • This pattern is the standard first step toward event-driven fintech systems: the keystone ledger project will emit transfer events through exactly this mechanism.
