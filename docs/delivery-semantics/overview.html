Delivery Semantics: Why Exactly-Once Is Something You Build

Between two separate systems, exactly-once delivery is impossible; exactly-once effect is an engineering pattern. The difference lives in one crash window every consumer has: the gap between processing a message and recording that it was processed.

TLDR

Quick brief
  • The impossibility is simple: apply-then-record duplicates on crash; record-then-apply loses on crash. No third ordering exists, so pick a side and engineer the consequence away.
  • At-least-once + idempotent processing = exactly-once effect. This is the standard answer, and the idempotency lives in the consumer, not the broker.
  • The cheapest dedupe is a primary key: insert the event id and apply the effect in the same database transaction; a replay conflicts and becomes a no-op.
  • Kafka EOS covers Kafka-to-Kafka. The moment a side effect leaves Kafka — a database row, an HTTP call — its transactions no longer protect you.

Mental Model

A consumer is a loop with two obligations per message: do the work, and move the bookmark. A crash can land between them, and the order you chose decides what the restart does:

at-most-oncemove bookmark → CRASH → work never happens; restart skips it
at-least-oncedo work → CRASH → bookmark stale; restart redoes the work
idempotentdo work + remember event id atomically → redo becomes a no-op

With money, the three have names: at-most-once loses credits, at-least-once double-credits, and idempotent balances to the cent. That is the whole topic; everything else is implementation.

Ground-Up Explanation

Why the network makes retries mandatory

A sender that gets no acknowledgement cannot distinguish "message lost" from "ack lost". If it cares about the message, it must resend — and if the ack was the thing that got lost, the resend is a duplicate. Retries are therefore not a bug source; they are the correctness mechanism, and duplicates are their unavoidable exhaust. Systems that "never duplicate" are systems that silently lose.

The idempotent consumer

The pattern that closes the loop is small enough to memorize:

BEGIN;
INSERT INTO processed_events (event_id) VALUES ($1)
  ON CONFLICT DO NOTHING;          -- 0 rows = already applied
-- only if the insert inserted:
UPDATE balances SET balance_cents = balance_cents + 100
  WHERE account_id = 'acct-1';
COMMIT;                            -- check and apply are one atom

The essential property: the duplicate check and the side effect commit together. Checking in Redis and writing in Postgres reintroduces the same crash window one layer down. Natural idempotency (e.g. SET status = 'paid') achieves the same end without the table, when the operation allows it.

What Kafka's "exactly-once semantics" actually is

Kafka EOS combines the idempotent producer (broker dedupes retries by sequence number within a partition) with transactions (atomic writes across topics, including the offsets topic). A consume-transform-produce pipeline can be exactly-once end to end within Kafka. It is genuine and useful — and it ends at Kafka's edge. Your database does not participate in a Kafka transaction; the idempotent-consumer pattern is still yours to build.

Lab Evidence

The runnable lab is labs/kafka/delivery: 1,000 payment events, each crediting 100 cents, applied to a Postgres balance by a consumer that hard-crashes (os.Exit, no cleanup) after event 500. The verify step compares the balance to the exact expected 100,000 cents.

make break

at-least-once: apply, crash, replay. Verify reports an overshoot and exits 1 — money was created.

make lose

at-most-once: commit, crash, skip. Verify reports a shortfall and exits 1 — money vanished.

make test

idempotent: same crash, dedupe insert in the credit's transaction. Verify is exact, exit 0.

Measured: the same crash, three balances

From real runs on 2026-07-07 (1,000 events, crash near event 500, offsets batch-committed every 100 messages):

at-least-once:  applied=600 after restart (100 replayed)
                balance=110000, expected=100000 → overshoot 10000. exit 1

at-most-once:   CRASH after committing offset for pay-499, before applying it
                balance= 99900, expected=100000 → shortfall 100. exit 1

idempotent:     applied=500 skipped-as-duplicate=100
                balance=100000, expected=100000 → exact. exit 0

The overshoot equals the replay window exactly: the last batch commit covered event 400, so 100 events replayed. The idempotent consumer replayed the same 100 and skipped every one inside the credit's own transaction.

Production Notes

  • Producers need stable event ids for consumer dedupe to mean anything. Generate the id where the event is born and carry it end to end — the same discipline as API idempotency keys.
  • The dedupe table needs retention (delete rows older than the topic's retention plus slack); it cannot grow forever, and it cannot be shorter than your replay horizon.
  • Dedupe keys must be scoped: event_id globally unique, or (consumer, event_id) when multiple consumers apply the same stream differently.
  • At-most-once has legitimate uses — metrics, ephemeral notifications — anywhere a loss is cheaper than a duplicate. Choose it explicitly, not by accident of commit order.
  • Reconciliation is the backstop: even with idempotency, fintech systems compare independent records (ledger vs provider reports) because bugs, not just crashes, create divergence.
