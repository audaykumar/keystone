Postgres Internals

MVCC · Vacuum · Locking · Indexes · Query Planner

Why this matters
Most production database incidents that look like app bugs are one of: a bloated table, a lock queue, or a bad query plan. MVCC explains all three root causes.

Basics Refresh

Postgres is an ACID-compliant relational database. A quick refresh on what that means at the storage level before going deeper.

How data is stored

Tables are stored as heap files — a collection of 8KB pages. Each page holds multiple tuples (rows). An index is a separate file with a B-tree (or other structure) pointing to heap locations.

MVCC — Multi-Version Concurrency Control

The mechanism that lets ordinary reads and row writes proceed concurrently. Postgres keeps multiple versions of a row and uses a transaction snapshot to decide which version is visible.

xmin and xmax

Every tuple has two hidden system columns:

ColumnMeaning
xminTransaction ID that created (inserted) this tuple
xmaxUsually the transaction ID that deleted or superseded this tuple. It can also contain row-locking information.

Visibility is not a simple transaction-ID comparison. Postgres checks whether the creating and deleting transactions committed, whether they were active in the reader's snapshot, and whether the current transaction created the version.

UPDATE is INSERT + DELETE

Postgres never modifies a tuple in place. An UPDATE writes a new tuple version and marks the old one deleted by setting its xmax.

sequenceDiagram participant T1 as Transaction 100 participant Heap as Heap Page T1->>Heap: INSERT row A → tuple (xmin=100, xmax=0) Note over Heap: row A visible, alive T1->>Heap: UPDATE row A → new tuple (xmin=100, xmax=0)
old tuple: xmax=100 Note over Heap: snapshot rules decide which version each reader sees

Snapshots and isolation levels

A snapshot records which transactions are visible to a statement. At the default READ COMMITTED level, each statement gets a new snapshot. REPEATABLE READ and SERIALIZABLE keep one snapshot across the transaction, beginning with its first relevant statement.

Key insight
Ordinary reads do not block ordinary row writes, and row writes do not block ordinary reads. DDL and explicit locks can still block them. Keeping row versions for MVCC creates dead tuples that vacuum must reclaim.

HOT updates

Heap Only Tuple update. If the updated column is not indexed and the new tuple fits on the same page, Postgres can skip updating the index entirely. The index still points to the old tuple, which chains to the new one. Significant write amplification saving.

Vacuum

MVCC leaves dead tuples behind. Vacuum reclaims that space. Without it, tables grow forever and performance degrades.

Autovacuum

Postgres runs autovacuum workers in the background. For updates and deletes, the trigger combines a fixed threshold with a fraction of the table size. The default scale factor is 20%. High-churn tables often need lower per-table settings:

-- Tune per-table for high-churn tables
ALTER TABLE transfers SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- trigger at 1% dead tuples
  autovacuum_analyze_scale_factor = 0.01
);

The long-transaction trap HIGH RISK

Vacuum cannot remove a dead tuple while an old snapshot might still need it. A long-running transaction can therefore hold back cleanup of newer dead tuples.

Incident pattern
A table keeps growing even though autovacuum runs. Check transaction age and snapshots in pg_stat_activity; common causes include sessions left idle in a transaction and long analytics transactions. 
-- Find blocking long transactions
SELECT pid, now() - xact_start AS transaction_age,
       state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
  AND xact_start < now() - interval '5 minutes'
ORDER BY xact_start;

-- Find sessions holding the oldest snapshots
SELECT pid, backend_xmin, state, query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC;

txid wraparound CRITICAL

Transaction IDs are 32-bit values interpreted within a roughly two-billion-transaction visibility window. If old row versions are not frozen before they fall outside that window, they could appear to belong to the future. Near that limit, Postgres refuses commands that need new transaction IDs.

graph LR A["Old tuple created"] --> B["XID counter advances"] B --> C["Autovacuum freezes old tuple"] B --> D["No freeze near safety limit
new XIDs refused"] style D fill:#2a1010,stroke:#f85149,color:#f85149

Postgres prevents this by freezing old tuples — marking them as visible to all future transactions. Monitor with:

-- Tables closest to wraparound (act if age > 1.5B)
SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY age(relfrozenxid) DESC
LIMIT 10;

The ALTER TABLE lock queue problem HIGH RISK

Many ALTER TABLE forms take ACCESS EXCLUSIVE, although some subcommands use weaker locks. If such an ALTER queues behind a long SELECT, later SELECTs can queue behind the waiting ALTER and effectively take the table offline.

sequenceDiagram participant S1 as SELECT (running, 5min) participant A as ALTER TABLE participant S2 as SELECT (new) participant S3 as SELECT (new) S1->>DB: Running (holds ACCESS SHARE) A->>DB: Waiting for ACCESS EXCLUSIVE Note over A,DB: ALTER queued — blocks here S2->>DB: Waiting (blocked behind ALTER) S3->>DB: Waiting (blocked behind ALTER) Note over S2,S3: Table effectively offline
Safe pattern
Always set lock_timeout before a migration. If the lock can't be acquired quickly, abort and retry during low traffic — don't let it queue.

SET lock_timeout = '2s'; ALTER TABLE ...

FOR UPDATE vs SKIP LOCKED

FOR UPDATESKIP LOCKED
BehaviourLocks selected rows, blocks other transactions trying to lock same rowsSkips rows already locked by other transactions
Use casePessimistic locking (prevent concurrent modification)Work queue — multiple workers pull jobs without blocking each other
-- Work queue pattern: each worker atomically claims a job
UPDATE jobs
SET status = 'processing', worker_id = $1
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;

Advisory locks

Application-level cooperative locks — Postgres stores them but your app decides what they mean. Useful for preventing concurrent runs of a job, or implementing distributed mutex patterns.

-- Acquire advisory lock (returns false if already held)
SELECT pg_try_advisory_lock(12345);

-- Release
SELECT pg_advisory_unlock(12345);

Indexes

B-tree (default)

Balanced tree with logarithmic search. Supports equality, ranges, and ordered scans. Prefix LIKE queries can use it when the collation and operator class permit. It is the default choice for common scalar lookups.

Partial indexes HIGH VALUE

Index only rows matching a WHERE clause. Smaller, faster, cheaper to maintain.

-- Only index pending jobs (not the 99% that are completed)
CREATE INDEX idx_jobs_pending ON jobs (created_at)
WHERE status = 'pending';

Covering indexes (INCLUDE)

Store extra payload columns in the index so a query can use an index-only scan. Heap visits are avoided only for pages marked all-visible in the visibility map.

-- Makes an index-only scan possible for this query shape
CREATE INDEX idx_transfers_covering
ON transfers (account_id)
INCLUDE (id, status, amount);

When the planner ignores your index

  • Low selectivity — when many rows match, a sequential scan may be cheaper; there is no universal percentage cutoff
  • Stale statistics — run ANALYZE
  • Incompatible expression or cast — applying a cast to the indexed column can prevent use of its normal operator class
  • Function on column — WHERE lower(email) = 'x' skips index on email; create a functional index instead
  • LIKE with leading wildcard — LIKE '%foo' can't use B-tree

Query Planner

The planner chooses how to execute a query. It estimates the cost of each possible plan and picks the cheapest. Bad estimates = bad plans.

EXPLAIN basics

-- Show plan without running
EXPLAIN SELECT * FROM transfers WHERE account_id = 42;

-- Run it and show actual vs estimated
EXPLAIN ANALYZE SELECT * FROM transfers WHERE account_id = 42;

-- Full detail: actual rows, buffers, timing
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM transfers WHERE account_id = 42;

Row estimate mismatch — a common cause of bad plans

If rows=1 but actual rows=50000, the planner made a poor cardinality estimate and may have chosen the wrong strategy. Refresh statistics first; for skewed columns, raise the per-column statistics target.

-- Refresh statistics
ANALYZE transfers;

-- Increase stats target for skewed column
ALTER TABLE transfers ALTER COLUMN status
SET STATISTICS 500;
ANALYZE transfers;

-- Inspect what Postgres knows about a column
SELECT * FROM pg_stats
WHERE tablename = 'transfers' AND attname = 'status';

WAL — Write-Ahead Log

Postgres records changes in WAL and guarantees that each WAL record reaches durable storage before its corresponding dirty data page does. This enables crash recovery and provides the stream used by physical replication and logical decoding.

sequenceDiagram participant App participant WAL participant Heap participant Replica App->>Heap: Modify page in shared memory App->>WAL: Append change and commit records WAL->>WAL: Flush WAL to durable storage WAL-->>App: Commit confirmed Heap-->>Heap: Dirty page written later WAL-->>Replica: Stream WAL records

LSN means Log Sequence Number: a position in the WAL stream. Logical-decoding and CDC systems use source log positions to preserve ordering and resume safely; wall-clock timestamps are not a reliable ordering mechanism.

-- Current WAL position
SELECT pg_current_wal_lsn();

-- Replication lag (on primary)
SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;
