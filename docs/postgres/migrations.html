Zero-Downtime Migrations

A schema migration is a deploy against shared mutable state. The danger is almost never the change itself; it is what the change locks, and who queues behind that lock while your traffic is live.

TLDR

Quick brief
  • The killer is the queue: an ALTER TABLE waiting for its lock makes every query issued after it wait too. A millisecond catalog change becomes a 30-second outage because a reporting query was still running.
  • Always set lock_timeout: a migration that gives up after one second and retries later is an inconvenience. A migration that waits indefinitely is an incident.
  • Plain CREATE INDEX blocks writes for the whole build. CONCURRENTLY trades speed and transactional safety for keeping writes flowing.
  • Big changes ship in small steps: expand (add nullable), backfill in batches, then contract (CHECK ... NOT VALID → VALIDATE → SET NOT NULL). No step holds a long exclusive lock.

Mental Model

Every statement in PostgreSQL takes a lock on the tables it touches, and locks are granted strictly in arrival order. Think of each table as having a single queue at its door. A SELECT only needs the weakest ticket (ACCESS SHARE) and walks in alongside other readers and writers. ALTER TABLE needs the strongest ticket (ACCESS EXCLUSIVE): it must wait until everyone inside leaves, and while it stands in the doorway, nobody else gets in — not even readers who would normally coexist with everything.

That doorway picture explains the classic production failure. The migration is not slow. The migration is polite, and PostgreSQL's queue fairness turns its politeness into a blockade.

Ground-Up: What Locks What

PostgreSQL has eight table-level lock modes, but three cover most migration reasoning:

LockTaken byConflicts with
ACCESS SHAREevery SELECTonly ACCESS EXCLUSIVE
SHAREplain CREATE INDEXall writes (INSERT/UPDATE/DELETE)
ACCESS EXCLUSIVEmost ALTER TABLE forms, DROP, TRUNCATE, VACUUM FULLeverything, including SELECT

Two facts complete the model. First, locks are held until the transaction ends, not until the statement ends — a transaction that touched orders ten minutes ago still holds its ACCESS SHARE lock. Second, waiters are granted in order, and a waiting stronger lock blocks later weaker requests. That second fact is the lock-queue outage.

Concept Deep Dive: The Three Failure Modes

1. The lock-queue outage

The ALTER itself, adding a nullable column, is a catalog update that takes about a millisecond once the lock is granted. But it cannot be granted while any transaction, even an idle one, holds any lock on the table. While the ALTER waits, all new queries queue behind it. The fix is not to avoid the ALTER; it is to bound the wait:

SET lock_timeout = '1s';
ALTER TABLE orders ADD COLUMN note text;
-- on failure: sleep, retry; each attempt costs at most ~1s of queueing

With the timeout, the worst case shifts from "site down until the reporting query ends" to "p99 blips ~1s per attempt". The migration tool owns the retry loop.

2. The blocking index build

Plain CREATE INDEX holds SHARE for the full scan-and-build: reads continue, every write blocks. On a 300k-row table that is seconds; on a real table it is minutes to hours. CREATE INDEX CONCURRENTLY does two passes plus a wait for concurrent snapshots to finish, so writes keep flowing. Its costs are real: roughly twice the build time, it cannot run inside a transaction block, and if it fails it leaves an INVALID index you must drop and rebuild.

3. The full-scan constraint

A bare ALTER TABLE ... ALTER COLUMN region SET NOT NULL must scan the whole table to prove the invariant, under ACCESS EXCLUSIVE. The expand-contract sequence gets the same end state without a long exclusive hold:

-- expand: catalog-only
ALTER TABLE orders ADD COLUMN region text;

-- backfill: batched, each batch its own transaction, pause between
UPDATE orders SET region = ... WHERE id IN (SELECT id FROM orders WHERE region IS NULL LIMIT 5000);

-- contract: instant, applies to new writes only
ALTER TABLE orders ADD CONSTRAINT orders_region_not_null CHECK (region IS NOT NULL) NOT VALID;
-- full scan, but under SHARE UPDATE EXCLUSIVE: reads and writes continue
ALTER TABLE orders VALIDATE CONSTRAINT orders_region_not_null;
-- PG12+: proven by the valid CHECK, so catalog-only
ALTER TABLE orders ALTER COLUMN region SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_region_not_null;

The same expand-contract shape covers column renames and type changes: add the new column, dual-write from the application, backfill, switch reads, drop the old column. Each deploy is individually boring, which is the point.

Implementation Details

  • Adding a column with a default is catalog-only since PostgreSQL 11 for constant defaults. A volatile default (now(), gen_random_uuid()) still rewrites the table.
  • lock_timeout vs statement_timeout: the first bounds waiting for a lock, the second bounds total statement runtime. Migrations want a short lock_timeout and a generous statement_timeout.
  • Batched backfills commit per batch. One giant UPDATE holds row locks and bloats the table in one shot; batches with pauses let vacuum, replicas, and application traffic breathe.
  • Idle-in-transaction sessions are silent blockers. An ORM connection that opened a transaction and went idle holds its locks indefinitely. idle_in_transaction_session_timeout is the guard.
  • Watch the queue live: pg_blocking_pids() joined against pg_stat_activity shows exactly who blocks whom (the lab's make locks).

Lab Evidence

The runnable lab is labs/postgres/migrations: a 300k-row orders table, a Go load driver printing per-second p50/p99/max latency, and each failure mode as a Make target run against live traffic.

make break

30s reader + unguarded ALTER. The load terminal shows ops drop to zero for the full reader duration.

make test

Same scenario with lock_timeout='1s' + retry. Load shows ~1s p99 blips instead of a stall.

make index-break / index-safe

Plain index build stalls INSERTs; CONCURRENTLY keeps them flowing, measurably slower to finish.

Measured: the same migration, two outcomes

From a real run on 2026-07-07, load at ~900 ops/s. Without lock_timeout, the load driver recorded 27 consecutive seconds of zero completed queries while the ALTER waited behind a 30s reader:

t=  8s ops=  611 errs=0 p50=6.9ms    p99=22.1ms   max=26.6ms
t=  9s ops=0 errs=0  << STALL: no query completed this second >>

With SET lock_timeout = '1s' and a retry loop (success on attempt 10), the worst any query saw in the entire run was 1.03s:

t= 12s ops=  188 errs=0 p50=6.4ms    p99=1.0276s  max=1.0324s
t= 16s ops=  948 errs=0 p50=6.1ms    p99=25.7ms   max=1.0343s
done. worst single-query latency or stall: 1.0343s

The batched backfill filled 329,081 rows in 66 committing batches (9.7s total); the NOT VALID → VALIDATE → SET NOT NULL contract step took 0.111s; CREATE INDEX CONCURRENTLY finished in 0.242s with no recorded write stall.

Production Notes

  • Encode the rules in tooling, not memory: GitLab's migration helpers and strong_migrations exist because humans forget at 2am.
  • Deploys and migrations are separate events. The application must run correctly against both the old and the new schema, because they will coexist during rollout — and during rollback.
  • Replicas replay ACCESS EXCLUSIVE locks too: a long lock on the primary can stall read replicas or conflict with replica queries.
  • High-frequency tables need extra care: even a 1s lock_timeout retry loop on a payments table deserves an off-peak window.
