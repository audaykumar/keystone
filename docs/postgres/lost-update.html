Lost Update & the Ledger Invariant

Part 1 · Schema and the invariant · labs/postgres-concurrency

Mental model
A ledger stores money twice. Once as an immutable list of debits and credits (postings), which is the truth. Once as a single mutable running total (accounts.balance), which is a cache for fast reads. Every concurrency bug in this lab lives in the gap between the two. The truth is hard to corrupt because each posting is its own row. The cache is easy to corrupt because concurrent writers fight over one number.

What the race button simulates
Two transfers run at the same time. Both read balance = B, both compute B − 1 in application memory, both write B − 1 back. The second write overwrites the first: one decrement is lost. The postings are unaffected (two separate INSERTs both land), so the truth still says −2 while the cache only moved −1. That difference is a lost update, and it is exactly what make break will reproduce against real PostgreSQL.

The Three Tables

Money is stored in minor units (cents) as bigint. Never floats for money: 0.1 + 0.2 ≠ 0.3 in binary floating point, and a ledger that rounds is a ledger that leaks.

accounts — the cache that gets corrupted

CREATE TABLE accounts (
  id               text        PRIMARY KEY,        -- 'alice', 'bob'
  name             text        NOT NULL,
  initial_balance  bigint      NOT NULL,           -- set once at seed, never mutated
  balance          bigint      NOT NULL,           -- the mutable cache (the victim)
  version          int         NOT NULL DEFAULT 0, -- seam for a later optimistic-lock demo
  created_at       timestamptz NOT NULL DEFAULT now()
);

transfers — one row per transfer intent

CREATE TABLE transfers (
  id               uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  from_account     text        NOT NULL REFERENCES accounts(id),
  to_account       text        NOT NULL REFERENCES accounts(id),
  amount           bigint      NOT NULL CHECK (amount > 0),
  idempotency_key  text        UNIQUE,                 -- seam for a later idempotency slice
  created_at       timestamptz NOT NULL DEFAULT now()
);

postings — the immutable double-entry truth

CREATE TABLE postings (
  id           bigserial   PRIMARY KEY,
  transfer_id  uuid        NOT NULL REFERENCES transfers(id),
  account_id   text        NOT NULL REFERENCES accounts(id),
  amount       bigint      NOT NULL,          -- signed: debit negative, credit positive
  created_at   timestamptz NOT NULL DEFAULT now()
);

Each transfer writes two postings: −amount on the source, +amount on the destination. They sum to zero. That is double-entry bookkeeping: money is never created or destroyed, only moved.

The Invariants We Will Assert

#InvariantHolds when?
I1 For every account: balance == initial_balance + Σ postings.amount Breaks under naive concurrent writes. This is the lost-update detector.
I2 For every transfer: Σ postings.amount WHERE transfer_id = t == 0 Always holds. Each posting is an independent INSERT; concurrency cannot unbalance a pair.
I3 System-wide: Σ accounts.balance == Σ accounts.initial_balance Breaks under naive writes. Money conservation across the whole ledger.
Why this design is self-checking
Because initial_balance is frozen at seed time, the database carries its own ground truth. No external bookkeeping is needed to know whether the cache lied: make break just compares balance against initial_balance + Σ postings and prints the drift.

Design Choices Worth Noting

ChoiceWhy
bigint cents, never floatFloating point cannot represent most decimal money values exactly. Integers in minor units are exact and orderable.
initial_balance frozenGives the invariant a fixed reference point so the DB is self-describing. The checker needs nothing external.
gen_random_uuid()Built into PostgreSQL core since v13. No pgcrypto extension required.
version column (unused now)The seam for a later optimistic-locking variant (compare-and-set on version). Costs nothing to include up front.
UNIQUE (idempotency_key)The seam for a later idempotency slice: turn duplicate submissions into a DB-enforced invariant.
Signed posting amountsOne column expresses both debit and credit. A transfer is two rows summing to zero, which makes I2 trivial to check.
